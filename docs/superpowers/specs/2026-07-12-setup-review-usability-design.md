# Setup 审核可用性与 Dashboard 恢复设计

## 背景与目标

完成 QuickStart 后，只要知识切片仍需人工审核，Gateway 会把 `/` 重定向回 `/setup`。这是既有质量门禁，但当前页面没有解释阻断原因；同时页面刷新后没有恢复 `latestRun`，即使审核完成，“进入 Dashboard”入口也可能不出现。

审核接口已经返回标题、路径、模块、严重级别、内容摘要、问题原因、影响、建议和缺失信息，但当前 Vue 组件只展示标题与路径，也没有本页全选和取消全选。这使审核者既难以判断内容，也必须逐项操作。

本次目标：不降低知识质量门禁，在 Setup 内让用户看得懂阻断原因、能够批量选择当前页、能够基于现有审核数据作出判断，并在审核完成后可靠进入 Dashboard。

## 范围

### 本次实现

- Setup 初始化时恢复服务端 `latestRun` 与 `review` 状态。
- 待审核时明确说明 Dashboard 被阻断以及待处理数量。
- 支持“全选本页”“取消全选”、已选数量与批量提交。
- 审核项展示已有的摘要、模块、状态和问题解释。
- 筛选、搜索、刷新或提交后清理不可见的旧选择。
- 审核完成后立即且在刷新后持续显示“进入 Dashboard”。
- 为上述行为增加组件测试和真实浏览器验收。

### 明确不做

- 不提供“选择所有分页/所有筛选结果”，全选只作用于当前页可见项。
- 不绕过审核直接进入 Dashboard。
- 不允许发布 `error` 级别的阻断切片。
- 不新增审核详情 API，不返回完整知识原文；先完整利用既有安全 DTO。
- 不改变现有 HTTP response shape、配置 shape、Case JSON shape 或知识 artifact shape。
- 不实现 LAN 鉴权。

## 方案选择

采用“信息展开的审核卡片”方案：每张卡片直接展示判断所需信息，顶部提供本页批量选择。相比详情抽屉，它减少批量审核中的反复打开操作；相比表格与独立详情页，它不改变 Setup 信息架构，也不需要新增接口。

## 模块归属与边界

- `web/src/setup/use-onboarding.ts` 负责把 `/api/onboarding` 的公开快照恢复为前端状态，并在审核提交后同步最新审核状态。
- `web/src/setup/App.vue` 负责展示 Setup 流程状态、审核门禁说明和 Dashboard 入口。
- `web/src/setup/ReviewPanel.vue` 只负责选择、筛选和审核信息展示，不自行决定哪些质量级别可发布。
- `src/onboarding/` 继续拥有审核业务规则；既有服务端规则仍禁止批准 `error` 项。
- `src/gateway/` 继续只负责路由与序列化；本次不修改首页门禁规则。

前端不得复制服务端质量决策。即使 UI 禁用不合法操作，服务端仍是最终权威。

## 状态与数据流

### 页面初始化

1. Setup 请求 `GET /api/onboarding`。
2. `useOnboarding` 保存公开快照，并把 `latestRun` 写入 `run`、把快照中的 `review` 写入 `review`。
3. 若审核仍为必需，再请求 `GET /api/onboarding/review` 取得完整当前页数据。
4. `App.vue` 根据恢复后的状态展示进度、门禁说明或 Dashboard 入口。

### 筛选与选择

- 当前页项目 ID 是选择范围的唯一来源。
- “全选本页”把当前 `items` 的 ID 写入选择集合。
- “取消全选”清空选择集合。
- 筛选、搜索、刷新完成后，选择集合与新页面求交集；若入口动作会改变列表，则直接清空，防止隐藏项目被误提交。
- 页面显示“已选 X / 本页 Y 条”。

### 审核提交

1. 用户选择当前页项目并选择发布、退回修改或不发布。
2. 组件只提交显式 `ids` 和备注，不使用空 ID 代表“全部”。
3. 服务端按现有规则处理并返回最新审核结果。
4. 前端以返回结果更新状态并重新加载当前审核页。
5. `required` 变为 `false` 后，门禁说明消失并显示 Dashboard 入口。

## 审核项展示

每项至少展示：

- 标题、来源路径和模块；
- `qualitySeverity`、`qualityStatus`、`pipelineStatus`；
- `excerptPreview` 内容摘要；
- 每个 issue 的消息、原因、影响、建议和缺失信息。

缺失字段不展示空占位；没有 issue 解释时仍展示摘要和状态。长内容保持可读换行，不把内部绝对路径、Secret 或 provider payload 引入页面。

## 错误与安全处理

- 待审核状态不是网络错误，使用说明性门禁提示，不使用失败告警样式。
- API 失败继续由 `useOnboarding.error` 进入可见错误 banner。
- 批量动作期间禁用重复提交。
- 选中 `error` 项时，“发布选中”不可用，并解释其必须退回修改或不发布；服务端校验继续保留。
- 筛选结果为空时显示空状态，不保留旧选择。
- 任何批量操作都必须携带非空显式 ID，避免后端“空 IDs 表示全部”的既有兼容语义造成误操作。

## 验收与测试

先失败后通过，覆盖真实生产组件与公开 HTTP 入口：

1. `ReviewPanel` 组件测试：
   - 渲染摘要、模块、状态、原因、影响、建议和缺失信息；
   - 全选只选择本页项目，取消全选清空；
   - 筛选或刷新后不可见项目不再被提交；
   - 批量提交只发送显式选中 ID；
   - 含 `error` 项时不能执行发布动作。
2. `App` / `useOnboarding` 测试：
   - 初始化恢复 `latestRun` 和 `review`；
   - 审核待处理时展示 Dashboard 阻断说明；
   - 已完成且无需审核时，即使刷新也展示 Dashboard 入口。
3. Playwright：通过真实 Node 服务完成 Setup 审核，验证批量选择、详情可见、审核完成后进入 `/`，刷新 `/` 仍停留 Dashboard。
4. 回归命令：

```bash
pnpm --dir web test --run
pnpm typecheck
pnpm build
pnpm test
pnpm test:e2e
```

## 完成标准

- 用户可以明确知道为何暂时不能进入 Dashboard。
- 用户无需逐个勾选即可选择或取消选择当前页全部项目。
- 用户无需仅凭文件名判断，页面提供现有 DTO 中全部关键审核依据。
- 审核完成后无需重新执行配置即可进入 Dashboard，刷新状态也正确。
- HTTP DTO、Gateway 门禁、LAN 无鉴权策略和服务端审核安全规则保持兼容。
